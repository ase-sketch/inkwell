# ADR 0005 — 双时间轴、向量持久化与查询计划（2026-07-31）

正式实现阶段第一轮。三件事：把时间从单轴扩成双轴、把向量从内存搬到磁盘、把多跳检索表达成可执行的计划。

## 1. 双时间轴

### 背景

spike 期只有 `tick`（宿主发放的全序整数）和 `time`（自由字符串，纯展示、不可比较）。`tick` 说不出「多久」——t12 与 t13 之间是五分钟还是三年，它没有这个信息。「三天后」「上个月」这类问题因此答不了。

### 决策

| # | 决策 | 理由 |
| --- | --- | --- |
| T1 | `tick` 保留为**摄入序 / 叙事推进序**，永远单调，仍是 as-of 知识边界的权威 | 它是既有全部正确性论证的地基（时间泄漏率 0%），且永远无歧义、零成本 |
| T2 | 新增可选 `instant`（bigint 秒，故事时间），**允许回退** | 倒叙 / 插叙 / 回忆章节里 tick 递增而 instant 后退，这是必须双轴的直接理由 |
| T3 | `asOfTick` 与 `asOfInstant` 两轴独立、同为 AND | 两者回答不同问题：知识边界 vs 世界状态，都成立 |
| T4 | 两轴皆缺省时才回落「当前认知口径」 | 否则按故事时间轴回溯会被摄入序轴的默认口径误杀已失效状态 |
| T5 | 别名 `sinceInstant`、ontology `atInstant`、state 有效区间全部双轴 | 「何时得知同一性」是认知事件：上帝视角按 tick（读者何时知道），角色视角按 instant（角色在故事时间的何时知道），见 ADR 0004 |
| T6 | 新增 `AsOf` 坐标类型，registry / state 的 as-of 参数由裸 number 改为坐标对象 | 把双轴变成类型事实，而不是到处并列两个参数 |
| T7 | **fail-closed**：查询给了某轴而记录缺该轴坐标 → 判不可见 | 无法安放的记录宁可漏召回，也不能泄漏进它可能并不属于的时间窗口 |
| T8 | Calendar **不进库**，走宿主注入；bigint 是为了与 World Engine 日历内核同构 | 历法是项目级资产，两个宿主的加载方式本就不同；只存 instant、不落人读串 = 改历法零迁移 |

### jsonl 里的 bigint

按**字段名白名单**在 bigint 与十进制字符串之间双向转换（`INSTANT_FIELDS`）。比 `{"$n":"..."}` 之类的标记法可读，jsonl 保持人可审、可 git diff。白名单外出现 bigint 直接抛错——新增故事时间字段却忘了登记时立刻炸，而不是静默退化成字符串。

## 2. 事实扩展字段

| # | 决策 | 理由 |
| --- | --- | --- |
| D3 | `Fact.meta` 只允许**扁平标量** | 过滤谓词要能用等值/集合表达；要能直接映射成 SQLite 生成列；开放嵌套结构会退化成无人负责的垃圾场 |
| D4 | 宿主**声明过**的 key 才可参与过滤，未声明的只存不滤 | 借 World Engine schema「宽松但有 kind」的思路：不挡路，也不失控 |
| D5 | 只开 `Fact` 一处，registry 与 state 不跟着开放 | 注册表刻意保持小是核心设计；state 的 topic/view 二元组已经够表达 |

一处扩展同时覆盖三个场景：群聊的 speaker/channel、ADR 0004 §4 的角色视角可信度标记、伴侣场景的 metric 事件标签。

## 3. 向量持久化

### 背景

旧实现向量全在内存，每次 `open` 都要把全库重新送去嵌入服务算一遍。几千条就是几十次 API 往返——这才是真实瓶颈，不是检索速度。

### 为什么不用向量虚表（vec0 之类）

本库的查询几乎永远带过滤：一次 `search` 实际发出「1 次主查询 + 每个提及主体 2 次 + 主体对若干次」约 10 个子查询，其中多数是重过滤、候选集只有几十条。

这种负载下「先过滤再精确扫描」的成本正比于**存活集**；ANN 索引则无论怎么过滤都要扫全图，还得靠超采后截断来近似过滤——那正是 as-of 泄漏的经典来源，本库明确拒绝。**成本模型是反的：过滤越严，暴力扫描越便宜，ANN 越无用武之地。**

主仓两套方案里，World Engine 的 `WorldPatch.vector` BLOB 列 + SQL 前置过滤 + 内存精确余弦，正是这个形态；`subject-rag-index` 的 vec0 + 4× 超采后截断则是被拒绝的那个。

| # | 决策 | 理由 |
| --- | --- | --- |
| S1 | 向量存普通 BLOB 列（Float32 小端），过滤走 SQL | 见上；比 JSON 浮点文本省约 5× |
| S2 | **下推谓词只能放宽，不能收紧**：`candidates()` 允许返回超集，权威判据只有 `passesFilter` 一份 | 「SQL 一份过滤、JS 另一份过滤」是让 as-of 零泄漏悄悄失效的最短路径。降级成纯 I/O 优化后，新增维度最坏只是没被下推 |
| S3 | `instant` 与 `meta` 暂不下推 | instant 以文本列存（保证 bigint 精确 roundtrip），字典序比较对不等长数字是错的；meta 等宿主声明可过滤 key 后用生成列承载 |
| S4 | 驱动用 `bun:sqlite` / `node:sqlite`，均为 runtime 内置 | 零 native 编译。被禁的是需要 node-gyp 的 **better-sqlite3**，不是 SQLite 本身——这一点 spike 期表述得过窄 |
| S5 | 换 embedding 模型只清空向量列渐进重嵌，**不报错、不要求删库** | 记忆库是长期资产，换个嵌入模型不该要求用户清空记忆（主仓 subject-rag 是直接报错要求删库，对缓存合适，对记忆不合适） |
| S6 | BM25 倒排留内存、从 store 重建，不落盘 | 倒排比向量小两个数量级，重建是纯 CPU 零 API 调用 |
| S7 | int8 量化**暂不做** | 真实规模（小说 2 万、伴侣 5 万）下 Float32 扫描是几十 MB，够用；等真到十万级再做 |

### 嵌入时机：录入 vs 查询

采用**混合**：默认录入时嵌入（可批、可预算），`deferEmbedding` 开启后只落库不嵌入、由 `backfillVectors()` 补齐。

关键保障：**字面路不需要任何向量**，所以向量没就绪时检索仍能返回结果，只是少了语义路。优雅降级是双路架构白送的，单路系统做不到。但必须**显式暴露** `pendingVectors`——静默降级比慢更危险，上层会把半成品当成全部记忆。

查询时嵌入的唯一致命细节是**必须写回**。主仓 World Engine 的 `resolveSearchVectors`（`world-engine.service.ts:526-549`）嵌完没有写回——`updatePatchVector` 全仓只在 `:451` 的 `vectorize()` 里调用一次，于是每次 `searchText` 都在重嵌同一批行。没有写回的 lazy = 每次全价重算。

## 4. 查询计划

### 背景

现有 `search` 的主体锚点来自「问题文本里字面提到的主体」。「昨天遇到的女孩，头发是什么颜色？」里没有专名，锚点就断了。

### 决策

| # | 决策 | 理由 |
| --- | --- | --- |
| P1 | 用 **JSON 计划**，不发明检索 DSL | DSL 要写 parser、要教模型语法、出错难 debug；JSON 计划模型天生会输出，且能直接映射到 `SearchOptions` |
| P2 | 计划必须**可缓存、可回放、可评测** | 同一个计划跑两遍结果一样，能离线打分——调优阶段的决定性差别 |
| P3 | 三种产出方式（启发式 / 便宜模型 / 手写）**共用同一份 schema** | 谁产出计划是宿主的选择，执行器完全一样；便宜模型的计划质量可以拿主模型的计划做离线对照 |
| P4 | 执行计划**零 LLM** | `findSubjects` 是纯倒排 + 注册表求解；LLM 只出现在产出计划这一步 |
| P5 | 规划失败一律降级为朴素单步计划，并如实返回 `degraded` | 检索基线（0 次 LLM + 1 次 embed）必须永远可用，增强路径不能变成必经之路 |
| P6 | **日历表达只在有 instant 时解析**，否则记入 `unresolved` | tick 是摄入序不是时间，硬映射会得到看似能用、实则随语料密度漂移的窗口，比不解析更糟。「刚才 / 最近」是例外——它们问的本来就是摄入序语义 |
| P7 | 便宜模型规划必须拿到**注册表快照** | 便宜模型的指代消解能力是该方案的天花板，而快照比同等 token 的对话原文信息密度高一个数量级；指代本来就该查注册表不该靠猜 |

### 方案 A / B 的取舍（记录，未实现 A）

- **A（主 session 直接调工具）**：效果最好，能吃到 prompt cache。真正代价不是「多一次长上下文调用」，而是**多一个串行 round trip**（决定查什么 → 等结果 → 再生成），用户感知延迟约等于两次长上下文推理；还有一个隐性代价是**污染主 session 的注意力**，长对话里模型该查时不查。
- **B（截断上下文 + 便宜模型）**：可并行（不依赖主 session，用户输入落地即可发出）、可评测。作为默认。
- **C（启发式）**：零 LLM，覆盖常见轮次，没命中再降级到 B。

## 5. 顺带修掉的两处真实浪费

1. **门面每次检索对同一个 query 调 10 次 embedding**——每个子查询各嵌一次。改为嵌一次复用到底。
2. **SQLite wrapper 每次调用都新 prepare 且从不 finalize**——既丢语句缓存，也让 Windows 下 close 后文件句柄不释放（表现为删不掉 .sqlite）。
