# 功能缺口调研（第三轮，2026-09-21）

> **2026-09 调研档案，决策已落地，仅存档。**
> 服务 M2+ 里程碑规划。用户体感「功能似乎少了什么但说不出来」，派两路子代理分视角盘点：
> 写作工具面（码字体验）+ AI 协作与作品管理面。本文档是合并去重后的结论。
> 前两轮已覆盖：机制层（2026-09-20-peer-projects-absorb.md）、布局层（2026-09-20-peer-layout-research.md），不重复。

## P0 — 缺失伤核心体验

| 缺口 | 同行参照 | 吸收方式 |
|---|---|---|
| 字数统计与码字目标 | easy-writing、起点/番茄助手、Scrivener | 编辑器底部常驻状态栏「本章 X 字｜今日 X 字」，点击设目标 |
| 分卷与章节层级 | easy-writing、Scrivener Binder | manuscript/ 支持一级分卷目录；正文树折叠分卷、拖拽调序 |
| 中文网文排版与敏感词自查 | easy-writing、番茄助手 | 段首缩进两全角空格开关；本地违规词高亮 + 一键排版 |
| 卡文追问（划词微访谈） | Storyteller/InkOS 三连问 | 编辑器选中文本 → 「卡文追问」带选段发问；小切口连珠问（意图/阻力/代价）。与 M2 计划重合 |
| 长篇上下文策略 | SillyTavern World Info、NovelForge 滑动视窗 | 恒定注入未决问题清单；提及实体时正则命中按需注入 lorebook 条目；拒绝全文盲喂 |

## 明确排除

- AI 续写 / 润色 / 扩写：硬红线
- 打字机音效等修饰玩具：增噪不增效
- 多书共享宇宙：单书流程未闭环，M5 后再议
- 移动端 App：违背桌面工具定位，用收件箱机制替代

## 机制层吸收：Skill 双轨制（用户点名，2026-09-21 专项调研）

第一轮调研吸收了写作 Skill 项目（chinese-novelist-skill、screenwriting-skills 等）的方法论，但漏了「skill 机制」这个形态本身——用户指出后补查，结论：**这是交付机制的缺口，不是某个功能的缺口**。

- **同行形态**：SKILL.md + YAML frontmatter（name/description），正文是方法论 SOP，复杂技能挂辅助 markdown/JSON 量表；宿主扫描目录按描述语义触发，也支持显式唤起；git 仓库即拷即用，有公共市场。
- **对作者的价值**：创作流派碎片化（爽文黄金三章/救猫咪/本格推理……），没有一套硬编码 profile 能通吃；作者长于文字、绝缘 TSX——markdown 技能包就是「追问库 + 审稿 Checklist」，可手搓、可网盘分享、即拷即生效。Inkwell 现有 TSX profile 需编译、只有开发者能写。
- **推荐方案 C 混合双轨**（否了纯 markdown 重写和 profile 可视化编辑器）：profile 管骨架与红线（固定访谈/追问/审稿 3-4 个内置角色），skill 管方法论（.nbook/skills/{name}/SKILL.md，作者可装可写，运行时注入上下文）。
- **红线不靠自觉靠机制**：交互型 profile 物理上不挂正文目录写工具（只开放备忘/批注写入），skill 再野也落不了盘；profile 系统提示词置顶声明「skill 仅作分析参照，一律不输出正文」。

## 给里程碑规划的建议

P0 五项里「卡文追问」就是既定 M2；「长篇上下文策略」是 M2 的前置依赖（追问质量取决于记忆）。建议 M2 扩为「卡文追问 + 上下文策略」，字数统计/分卷/排版组成一个「码字基本盘」里程碑插到 M2 之后、M3 审稿之前。

Skill 双轨制建议**与 M2 同期落地骨架**：卡文追问本身就是第一个内置 skill 的天然载体——先把 .nbook/skills/ 扫描注入打通，M2 的追问库和 M3 的审稿量表都按 skill 形态交付，后续作者生态才有生长点。
