# 小说问答服务 Spike

> 状态：研究草稿，不是已实现能力或正式产品 Spec
> 建立日期：2026-08-26
> 样书：仓库本地资产 `.local/novels/转生反派萝莉，找茬魔法少女.epub`

## 1. 目标

研究一个用一本完整小说初始化的服务。初始化后，用户通过自然语言提问，在不阅读原文的情况下理解人物、剧情、关系、设定和前因后果；未来还可能把同一批理解产物用于说书。

目标是接近熟读全书的作者所具备的**知识覆盖、事实准确和因果解释能力**，不是模仿作者文风。摘要与中间产物应中性、信息密集，并能追溯到原文。

本轮只做需求与实验设计，不开发服务，不决定最终模型、NLP 库、存储 schema 或公开 API。

## 2. `nb-memory` 当前能力边界

这条边界是本 Spike 的硬前提：**`nb-memory` 当前能把调用方提供的文本加工成可检索记忆并召回证据，但不能直接准确回答整本小说的问题。**

### 2.1 当前真正存在的链路

`NbMemory.ingestRaw(inputs, options)` 对调用方提供的全部 `IngestRawInput[]` 执行：

1. 把每个 input 原文保存为 `Episode`；
2. 把 input 文本切成模型块；
3. 逐块调用 LLM，把原文改写成独立 `Fact`；
4. 分批再次调用 LLM，登记或更新 `Subject`、别名、本体描述和 `StateEntry`，并把事实关联到 `subjectIds`；
5. 把 fact、state 与 subject 描述写入字面/语义检索索引。

这是对已提供文本的同步、LLM 驱动加工。它没有导入一本书的概念，也不知道 input 是卷、章、场景还是任意文本。

`NbMemory.search(query, options)` 只返回 `Promise<SearchHit[]>`。命中项是 fact、state、subject 描述或注册表主体卡；它们是供上层回答模型使用的证据，不是最终自然语言答案。查询计划最终也只是组织多步检索并返回命中。

### 2.2 明确不属于当前 `nb-memory` 的能力

以下能力当前都需要宿主层提供，不能因 `ingestRaw` 或 `search` 存在而宣称已经解决：

- EPUB/TXT 读取、EPUB metadata/spine/TOC 解析；
- 书、卷、章、场景、段落及原文位置模型；
- 章节标题定位和原文引用范围；
- 词性、名词、人名、共指、对话边界、说话人和叙事视角标注；
- 章节/场景/剧情阶段/全书摘要及其缓存；
- 全书人物全集、主要人物排序和全局统计；
- “第 N 次发生某事”这类完整枚举与序数查询；
- 初始化任务、后台调度、断点续做、进度和派生产物失效；
- 问题分类、证据充分性判断、冲突处理和覆盖率判断；
- 最终自然语言答案、证据展示和说书稿生成。

其中部分能力未来可能适合下沉到 `nb-memory`，但必须由 Spike 证明它是通用记忆内核责任，而不是为了样书或单一宿主增加特例。

### 2.3 可以复用的内核

`nb-memory` 已有的 `Episode`、`Fact`、`SubjectRegistry`、`StateEntry`、别名揭晓时点、双时间轴、主体对查询、BM25/语义融合和可重放派生层，适合承载小说理解后的事实记忆与证据检索。

特别是：

- `tick` 可表达读者读到某处时知道什么；
- `instant` 可表达故事内实际时间，允许倒叙和插叙；
- alias 的生效时点可避免身份尚未揭晓时提前泄底；
- state 的取代链可表达关系、认知和处境的变化。

这些是回答系统的一个内核，不是完整回答系统。

## 3. 代表问题：按能力难度递增

后一级问题包含或依赖前一级能力。只选这些问题做纵向验证；它们通过后，原先大量问法会成为同一能力的参数变化，而不是新的系统能力。

### L1：定位并概括一个明确章节

> “狐狐的大戏”这一章讲了什么？

需要：EPUB 章节定位、长章切分、局部摘要、人物/事件提取、原文证据和答案生成。

这是最低难度的完整纵向链路。范围由章节标题明确给出，不需要先解决全书实体或跨章聚合。

### L2：解释一个自然语言称呼

> 金毛狐狐是什么？

需要：判断问题问的是词语、物种、外貌还是实体；把“金毛狐狐”与苏天晴及其他别名/身份归一；召回定义和上下文；生成带证据的解释。

相较 L1，新增的是实体发现、指代消解和别名归一。相似文本命中本身不能证明“它指谁”。

### L3：列出全书人物并判断主次

> 这本书有哪些人物？哪些是主要人物？为什么？

需要：全书覆盖、人物候选发现、跨章实体归一、无名角色处理、完整性判断，以及基于章节跨度、关键事件、关系和因果作用的主次排序。

这是第一个全局问题。top-k 检索不能证明“所有”；主要人物也不是提及次数排序。

### L4：解释一段关系如何变化

> 苏天晴和某个主要人物的关系经历了哪些阶段？每次变化由什么事件触发？

需要：跨章关系事实、状态取代、时间排序、关键转折筛选和因果证据。

相较 L3，新增的是同一关系的历史版本、阶段划分和因果解释，而不只是静态人物卡。

### L5：回答特定阅读进度下知道什么

> 只读到第 150 章时，读者会怎样理解某个身份或秘密？后来哪一章改变了这个理解？

需要：叙事顺序、身份揭晓、别名生效、状态修正和 as-of 知识边界，且不能把后文真相泄漏进前文答案。

这是 `nb-memory` 双时间轴和 alias 历史最有直接价值的问题，但前提仍是宿主正确解析章节并提供稳定的叙事坐标。

### L6：定位某类事件的第 N 次发生

> 苏天晴第三次使用某项能力是在什么时候？当时发生了什么？

需要：全书完整事件发现、同类事件归一、否定与回忆区分、叙事顺序/故事时间选择、序数计算和原文复核。

这比“搜索一次相关事件”难得多。系统必须证明前两次没有漏掉；语义 top-k 召回无法提供这种完整性。

### L7：把全书讲给没读过的人

> 用 15 分钟讲清楚整本书，保留主线、人物转折和关键因果，不写成逐章流水账。

需要：前六级能力、分层摘要、剧情阶段划分、重要性排序、重复压缩、悬念释放和面向口播的重写。

说书不是拼接章节摘要。它要求全书结构理解和叙事组织，是本 Spike 的最高难度目标。

## 4. 从代表问题得到的最小能力集合

当前实现位置与未来 owner 分开判断：`当前实现位置`只陈述今天代码在哪里；`目标研究方向`允许把通用小说理解能力扩展进 `nb-memory`，再向 NeuroBook 产品系统投影。

| 能力 | 首次被哪个问题要求 | 当前实现位置 | 目标研究方向 |
|---|---|---|---|
| 书籍解析与来源定位 | L1 | `nb-memory` 外部 | 评估作为 `nb-memory` ingest adapter 或宿主 loader |
| 章/场景/模型块三层切分 | L1 | `nb-memory.chunk` 只有模型输入块 | 扩展通用来源单元与场景边界，保留章级来源身份 |
| 中性局部摘要与证据映射 | L1 | 未实现 | 作为通用小说理解产物进入 `nb-memory` 候选范围 |
| 实体发现、共指和别名候选 | L2 | `ingestRaw` 只做 LLM 事实抽取与后续主体消解 | 扩展首遍 brief，再投影到 `SubjectRegistry` |
| 全书覆盖与主要人物排序 | L3 | 未实现 | 由渐加处理覆盖率与全局聚合提供 |
| 关系/状态历史 | L4 | 宿主抽取，`nb-memory` 可承载与检索 | 评估由 brief ingest 统一生成 |
| 读者知识边界 | L5 | 宿主提供坐标，`nb-memory` 可承载与过滤 | 保持 `tick` / alias 历史优势，并与章节坐标对齐 |
| 完整事件枚举与序数查询 | L6 | 未实现 | 扩展可完整扫描的事件视图，不用 top-k 冒充全集 |
| 分层全书摘要与说书 | L7 | 未实现 | 摘要树进入理解层；说书仍是消费层 |
| World Engine 投影 | L1-L7 | 未实现 | 只投影需要随故事时间追踪的 subject 状态与关键 slice |
| PlotBench 投影 | L1-L7 | 未实现 | 投影 Story/Chapter/Scene/Thread 等作者视角剧情结构 |
| 最终答案与引用 | L1-L7 | `search` 仅返回 `SearchHit[]` | 消费层综合 brief、图谱和检索证据 |
| 调度、缓存、进度和失效 | L1-L7 | 未实现 | 全部处理与懒惰加载共用渐加任务协议 |

### 4.1 与 NeuroBook 拆书、World Engine、PlotBench 的关系

拆书和剧情理解使用同一条知识生成链：原文先形成可追溯 brief，再 ingest 成主体、事实、状态、关系和剧情结构。区别只在消费目的：拆书面向已有作品的结构化还原，剧情理解面向问答、续写、审查和说书。

- `nb-memory`：候选通用理解与检索层。保存原文 episode、事实、主体/别名、状态、摘要和证据索引，并支持按知识边界检索。
- World Engine：动态世界状态与故事时间线真相源。只接收会被后续剧情读取的主体状态和关键转折，不复制所有事实或章节摘要。
- PlotBench：作者视角剧情结构。消费章、场景、剧情线、目的、因果、节奏和伏笔；不保存动态世界状态。

同一 brief 可以生成三个视图，但不应把同一段文字无差别复制三份。`nb-memory` 保留可召回证据，World Engine 保留可 reduce 的动态状态，PlotBench 保留可编辑的剧情组织；跨系统用稳定来源锚和主体 identity 关联。

### 4.2 全部处理与懒惰加载是同一渐加协议

- **全部处理**：把当前作品全部来源单元推进到首遍 brief/ingest 完成，立即解锁依赖全书覆盖的功能。
- **懒惰加载**：只把满足当前问题或消费所需的来源单元推进到对应处理等级。
- **连载更新**：新增章节继续从未处理状态向前推进；已经完成的产物不因作品仍在连载而失效。

两种模式只差目标覆盖范围和调度优先级，不应维护两套处理实现。

词性标注和“获取所有名词”不是独立产品目标。它们可以作为实体候选的廉价召回信号，但无法独立解决实体类型、别名、共指、关系或主次判断。

“划分角色对话”也要拆成两级：用标点/版式识别直接引语边界相对容易；把话正确归给说话人和听话人，并判断内心、撒谎或讽刺，需要场景参与者和跨句语义。

## 5. 新洞察：全书小模型首遍处理可能很划算

先前草稿把“658 章至少 658 次调用”直接推成“成本不可接受”。这个推论不成立：请求次数本身不能决定总成本。对于一本边界固定、会被反复提问的小说，用本地模型或低价/免费小模型完整处理一次，可能比每次提问再按需回读和补分析更便宜，也更容易保证全局问题的覆盖率。

因此本 Spike 的默认候选不再是“只做懒加载”，而是：

1. 初始化时解析全书结构和原文位置；
2. 对全书所有来源单元执行一次便宜、可缓存的小模型首遍处理；
3. 建立局部摘要、实体候选、事件/状态/关系候选和证据映射；
4. 用首遍产物构建人物清单、剧情阶段等全局派生视图；
5. 仅对低置信度片段、复杂问题和更高质量说书按需调用更强模型。

这里的“全书摘要”是**全书覆盖的分层处理**，不是把整本小说塞进一次上下文，也不等于机械地每章一次：

- 章是原作来源结构，必须保留；
- 场景是摘要和事件理解单元；
- 模型块只受上下文窗口约束；
- 长章可拆多个场景和块；
- 没有章节的作品按段落、分隔符、时间地点变化和长度形成来源单元；
- 多个短章可以在更高层聚成同一剧情阶段。

### 5.1 为什么可能划算

- 成本一次发生，可被后续大量问题和说书复用；
- L3、L6、L7 这类问题本来就要求全书覆盖，纯懒加载无法证明完整；
- 小模型适合局部、结构化、可复核的摘要与抽取；
- 本地产物可缓存，问法变化不需要重新读原文；
- 后续大模型只消费压缩后的相关事实和摘要，减少重复长上下文成本。

### 5.2 仍需保留懒加载的地方

- 首遍处理失败或低置信度的片段；
- 说话人、隐含因果、伏笔等较难语义；
- 用户第一次提出的新分析维度；
- 高质量长答案和说书重写；
- 模型、提示词或 schema 变化后的局部失效重建。

全量首遍处理与懒加载不是二选一。候选形态是“便宜全量打底，昂贵能力按需深化”。

## 6. 首遍处理产物的工作假设

每个来源单元至少输出以下受约束产物，所有字段保留原文范围：

- 中性短摘要；
- 出场实体及其原文称呼；
- 事件列表；
- 状态和关系变化；
- 时间、地点和场景参与者；
- 关键对话候选及说话人置信度；
- 身份揭晓、疑似伏笔和无法确定项。

这不是最终 schema。需要实验比较三条路径：

1. 当前 `ingestRaw` 的“事实抽取 → 主体/状态消解”；
2. 独立的“结构化摘要 → 再投影到 `nb-memory`”；
3. 一次模型调用同时产出摘要和可投影事实。

选择标准是准确率、全书成本、可重放性和错误隔离，不以少一次调用为唯一目标。一个错误的合并调用可能同时污染摘要与事实层。

## 7. 答案合同

无论内部采用哪条路径，最终用户答案至少要有：

- **直接答案**：先回答问题；
- **证据**：章节号、标题、原文范围，必要时最小引文；
- **结论类型**：原文明示、跨证据推导、文学解读或无法确定；
- **覆盖率**：全局问题说明是否覆盖全部来源单元；
- **不确定性**：具体指出别名冲突、说话人不稳或因果仅为推断；
- **处理状态**：是否使用低成本首遍产物，是否触发更深分析。

准确性优先于流畅。`SearchHit[]` 只能作为证据输入，不能直接作为符合该合同的答案。

## 9. 首轮实验

### 实验 A：全书处理成本

解析 EPUB，测量总字符/token、章长和场景长度分布。选择至少一个候选小模型，对全书首遍处理，记录：

- 模型与量化版本；
- 本地硬件或远端价格；
- 输入/输出 token；
- 调用数、并发度、总耗时和失败重试；
- 产物体积；
- 首遍后 L1-L7 各问题还需要多少增量处理。

目标：用真实数字判断“全量打底”和“纯懒加载”的成本分界，而不是从 658 次请求推测。

### 实验 B：处理路径对照

在相同章节范围比较：

- `ingestRaw` 事实路径；
- 独立结构化摘要路径；
- 摘要与事实联合输出路径。

分别检查事实覆盖、实体归一、关系/状态变化、摘要文风污染、证据映射和失败后的重放范围。

### 实验 B.1：第一章纯文本摘要密度预实验

固定输入为 `OEBPS/chapter_00001.xhtml` 经 `chapter-source-normalization/v1` 处理后的同一正文：`textChars=2122`、`visibleChars=2044`、SHA-256 `22c9b12d0305da4b64ea39751e809ed47cf9254d574caf875fbff91ef82552ee`。三个等级共用 `opencode/deepseek-v4-flash`、system prompt、user 模板、独立上下文和 `maxTokens=4000`，只改变密度追加提示词。

- L1 v1 目标 `1000–1400` 可见字。前两次调用以脱敏类别 `client-failure` 结束；第三次成功输出 `742` 可见字，压缩率 `36.30%`。开发者否决该成品：它把原文从狐女房间开场、再回想五分钟前死亡的倒叙重排为时间正序，原对话和叙事过程保留不足，不能作为作者驱动写作模型复原章节的依据。
- L2 目标 `500–750` 可见字。实际 `607` 可见字，压缩率 `29.70%`，保留主线、主要名称和最终状态；但把原文倒叙改成时间正序，并漏掉实体别名、角色自称、契约阶段和多项未决线索，因此不适合作为唯一 ingest 输入。
- L3 目标 `180–300` 可见字。实际 `244` 可见字，压缩率 `11.94%`，保留“猝死重生 → 秘典诱签 → 反派魔法少女契约成立”的主因果链，删除外貌欣赏、职业风险数字等次要细节。

L1 不能只按事实覆盖验收。它的目标是作者交给写作模型的缩句指令：下游只看 L1，也应能复原场景顺序、倒叙/插叙位置、信息揭示、关键人物反应、承担人物声音的原对话，以及原文明示的心理活动。心理可以保留，但必须归属于角色；摘要者不能补充主观动机、因果或评价。

首份人工候选保留了上述信息，但达到 `1488` 可见字、输出保留率 `72.80%`，被开发者否决。第二份待审查候选只保留关键原话，其余对话客观转述，并试验 3 条“写作提示（系统提取）”：正文 `669`、系统提示 `183`，合计 `852` 可见字，输出保留率 `41.68%`、删减率 `58.32%`，满足本章 `<1000` 和至少删去一半的门槛。只有输入中已有的作者文字才能称为“作者批注”；模型自行从原文提取的内容必须标为系统写作提示，不能冒充作者意图。该方案仍待开发者审查，不计入 DeepSeek 模型对照统计；原始模型输出、统计、`chapter-001-brief.json` 和首份人工稿均保留为基线。

L3 在目标范围内并保持主因果链。L2 作为人读详细摘要基本成立，但作为实体抽取/ingest 输入未通过叙事顺序、实体别名、契约状态、不确定性和候选线索召回审查。L1 研究已暂停；L2 v1 原始输出保留，审计结论作为下一版 L2 合同依据，不覆盖模型 evidence。

修正审计后固定 L2/L3 v2 提示词并执行真实调用。L3 v2 成功，输出 `198` 可见字、保留率 `9.69%`，保持“先同意契约 → 后得知反派魔法少女内容 → 最后绑定与契约成立”的关键顺序；角色对高危职业和王道反派的判断保留了来源归属。L2 v2 初次调用和唯一授权重试均以脱敏类别 `client-failure` 结束，分别耗时 `30766ms`、`28931ms`，没有可见正文；因此不能评价 L2 v2 提示词的实际质量，也不能交付新版 L2 供审查。

开发者随后指定 DeepSeek 官方 API。provider `deepseek` / model `deepseek-v4-flash` 使用同一 L2 v2 固定提示词一次成功：`773` 可见字、保留率 `37.82%`、耗时 `11301ms`。成品改善了问名/相对时间锚、太奶画面、契约阶段、原身体主人疑问和任务未说明等召回；但仍把薅尾巴移到死亡回忆之前，并在初次照镜时提前泄露原文稍后才出现的睡裙，把古书疑问改成“制止”，造成“星界使者”主语歧义，漏掉“狐狐”“小破书”并新增“狐萝莉”，且未逐项保留全部未决边界。它还保留低辨识度问名原话，却删除或泛化小脚金句、独特称呼、活泼动作和王道反派吐槽，使苏天晴的性格和人物声音几乎不可见。因此 L2 v2 方向有效但仍未通过 ingest 合同，原始输出保留为 evidence，不人工改写。

L2 v3 将性格证据合同整理为完整冻结提示词，并通过 DeepSeek 官方 API 单次生成：`891` 可见字、保留率 `43.59%`、耗时 `5900ms`、脚本记录 HTTP 请求 `1`。人物声音显著改善，小脚金句、“好，我签”、两指/尾巴动作、财富与萝莉愿望及王道反派吐槽均被保留，仅看摘要已能感知苏天晴的偏好、俏皮表达、果断和类型意识。但成品把房间开场与“五分钟前”回忆彻底改成时间正序，漏掉开场问名、原身体主人认知、“小破书”和多项未决边界，“星界使者”主语仍含混，并超出目标上限 `41` 字。v3 官方直连使用 `thinking.type=disabled`，v2 经 pi-ai 使用 `reasoning:false`，二者未证实完全等价；v2/v3 不是严格的提示词单变量对照。调用脚本只校验第一候选正文非空，没有拒绝多候选响应，且响应封套未保存，因此实际 choice 数不可追溯。该实验确认性格证据适合进入 L2，但不能单凭当前对照量化提示词净效应，也未证明连续文本能兼任完整 ingest 清单。

L2 v4 加入感知来源和第一章 7 节点叙事骨架，并沿用 v3 的人物声音规则。DeepSeek 官方 API 单次生成 `1150` 可见字、保留率 `56.26%`、耗时 `6270ms`，严格观测一个非空候选。v4 恢复了原文倒叙、相对时间锚和 7 个主要节点的排列顺序，将太奶画面正确限定为苏天晴的临终感知并保持真实性/因果未知，也把尾巴触感保留为角色主观感叹；人物声音、原身体主人疑问和实际称呼均保住。但“节点排列通过”不代表节点内部通过：第 4 节仍有“星界使者”主语含混，第 6→7 节的奴隶契约心理顺序因 v4 提示词自身误写而出错；最佳适格者原因仍漏标未知，输出也超 L2 上限 `300` 字。v4 证明显式骨架与感知来源规则有效，也证明把全部 ingest 清单直接塞进连续摘要会导致密度失控，且无法消除所有局部错误。

### 实验 C：代表问题阶梯

按 L1 → L7 顺序建立问题与人工证据。每一级只在前一级通过后增加新能力，分别记录：

- 正确证据是否已进入派生层；
- 检索/聚合是否取到完整证据；
- 最终答案是否忠于证据；
- 首问与重复问的延迟、模型调用和缓存复用；
- 是否出现漏人物、错实体、错时间、旧状态、序数漏项或局部冒充全局。
