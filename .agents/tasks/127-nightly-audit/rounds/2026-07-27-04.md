## 发现

### 预期的那条不成立——备份的读取端是对的

`verifyManifest` 用的是**裸 `catch`**，不是「只兜 ENOENT」：

```ts
try {
    manifest = JSON.parse(await readFile(join(restoreDir, "nb-backup.json"), "utf8")) as {...};
} catch {
    throw new Error("归档缺少 nb-backup.json，不是合法的 NeuroBook 备份");
}
```

损坏和缺失都被转成了一句面向用户的领域错误。`readAppVersion`（33 行）同理。**F-006 / F-008 的模式在备份链上不成立**，上一轮的预判错了，如实记下来。

（唯一瑕疵：文件存在但 JSON 损坏时报的是「缺少」。用词不准，但用户的动作一样——换个备份，不改变任何决策，不记 finding。）

### F-009（high）：真正的问题是反过来的——catch 得太宽，静默丢数据

`backup-archive-service.ts` 里，**同一个文件同时存在正确写法和错误写法**：

**正确的**（165–173）：SQLite 快照失败 → 记 warning + 退化为原样拷贝，不中断。

```ts
} catch (error) {
    warnings.push(`SQLite 快照失败，已按原文件打包：${relative}（...）`);
    ...
}
```

**错误的**（47–53）：

```ts
async function collectFiles(dir: string, prefix: string, out: string[]): Promise<void> {
    let entries;
    try {
        entries = await readdir(dir, {withFileTypes: true});
    } catch {
        return; // 目录不存在（如全新实例无 workspace 子目录）
    }
```

注释写的是「目录不存在」，但裸 `catch` 连 `EACCES` / `EPERM` / `EMFILE` / `EIO` 一起吞了。**任何一个子目录读不动，整棵子树就从备份里消失**，而备份照样成功返回，带着 sha256、fileCount 和一个空的 warnings 数组。

用户拿到的是一个看起来完整、实际缺了几章正文的备份。**而他要到恢复的那一刻才会发现。**

`collectFiles` 的签名 `(dir, prefix, out)` 里根本没有 `warnings` —— **上报通道就在同一个文件里且工作正常，只是这里没接**。

同类第二处在 96–102 行：`stat` 失败静默跳过，注释写「不存在则跳过（dev 环境常无 config.yaml）」，同样会吞掉权限错误，让 `config.yaml` / `.env` 悄悄不进备份。后果轻一些（恢复出来的实例起不来，而不是丢正文），但是同一个毛病。

修法明确：`collectFiles` 与 96 行那处都改成**只把 `ENOENT` 当正常缺失**，其余错误接进已有的 `warnings` 通道；`collectFiles` 需要多收一个 `warnings` 参数。

### 今夜的判断因此要改写

前三轮的结论是「缺一个原子写 helper」。第 4 轮显示那只是一半。真正的共同点是：

> **代码没有一致地区分「预期内的缺失」和「意料外的失败」。**
>
> - F-006 / F-008 **兜得太窄**——只认 `ENOENT`，于是文件损坏直接把进程掀了
> - F-009 **兜得太宽**——裸 `catch` 全吞，于是真实错误变成静默丢数据
>
> 两个方向的症状相反，病因是同一个。而且这两处的注释都写着「文件不存在时……」——**写代码的人心里想的是 ENOENT，手上写的却是「所有错误」或「只有 ENOENT」**，两次都没对齐。

这个框架比「缺 helper」更有用：它同时解释了为什么修法不能一刀切（第 3 轮结论），也给出了统一的判据——**每个 catch 都要问一句：我想放过的是哪个 errno？**
