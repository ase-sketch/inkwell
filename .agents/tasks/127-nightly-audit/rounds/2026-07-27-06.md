### 26 项的根因（不是 finding，但早报值得提一句）

25 项 TS2345 全是同一句：

> `Property 'ignoreTerms' is missing in type '{...}' but required in type 'NormalizedLlmlintConfig'`

即 `NormalizedLlmlintConfig` 后来加了必填的 `ignoreTerms`，而 `llmlint.test.ts` 里的十几处配置字面量没跟上。剩下 1 项 TS2322 是 `'"module"' is not assignable to type '"builtin"'`。

**修法很小**：给测试里的配置字面量补 `ignoreTerms`，或抽一个 `makeConfig()` 帮手。见 F-012。

## 其余发现：两个负面结果，都是好消息

用剩下的预算做了原计划的第 1、2 项。

### 恢复侧不共享排除规则，F-010 不会二次放大

`backup-restore-service.ts` 只 import 了 `sanitizeZipEntryName`，**没有 import `shouldExcludeFromBackup`**。所以 F-010 只影响「打包时漏收」，不影响「恢复时漏出」。

不过 `backup-archive-rules.ts` 文件头写着「也让打包/恢复两侧共享同一判据」——**实际只共享三个函数中的一个**。注释说得比事实大，但不构成缺陷，不单列 finding。

### `sanitizeZipEntryName` 返回 null 的处理是对的

```ts
const safeName = sanitizeZipEntryName(file.name);
if (safeName === null) {
    failure = failure ?? new Error(`归档包含非法路径条目：${file.name}`);
    return;
}
```

`failure` 会被外层循环检出并 throw，**整个恢复中止**，不是静默跳过这一条。对 zip-slip 防护来说这是唯一正确的方向。目录条目也走同一道校验。

原以为这里会是「静默失败第三层」的又一例，**不是**。
