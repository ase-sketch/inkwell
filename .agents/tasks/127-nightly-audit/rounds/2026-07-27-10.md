## 先说好的：`file-path.ts` 是今夜读到的最扎实的一份代码

值得单独记，因为早报里会有人问「那这个仓库到底有没有写对的地方」：

- **branded type** `AbsoluteFsPath`，绝对路径不能靠 `string` 混进来
- **词法 containment 与真实 containment 分开**：`resolveContainedFilePath()` 做词法检查，`assertRealPathContained()` 补 symlink/junction 逃逸，注释明确写了前者「不会穿透已存在 symlink/junction」
- **rename/unlink 用父目录检查**（`assertRealParentContained`），因为这类操作作用于目录项本身、不应跟随目标 symlink——这个区分很多项目都不做
- `isOutsideRootRelativePath()` 正确处理了经典误报：只认 `".."` 与 `".." + sep`，不会把 `..foo` 这种合法文件名当成逃逸

没有在这个文件里找到缺陷。

## F-019（medium）：`installation-paths.ts` 的便捷层绕过了 `RuntimePaths` 自己划的边界

`runtime-paths.ts` 的设计意图写得非常清楚：

```ts
/**
 * 从已确定的Application Root与State Root建立Runtime Paths。
 * 本函数不读取cwd或环境变量；生产、开发和测试Adapter必须在调用前决定两个根。
 */
export function createRuntimePaths(...): RuntimePaths {
    return Object.freeze({...});
}
```

类型注释是「**一次NeuroBook进程使用的不可变物理根集合**」，返回值 `Object.freeze`。意图是**解析一次、往下传**。

但 `installation-paths.ts` 提供的六个便捷函数，每一个都是：

```ts
export function resolveStateRoot(startPath = process.cwd(), env: NodeJS.ProcessEnv = process.env): string {
    return runtimePathsFromEnv(startPath, env).stateRoot;
}
```

**默认参数在每次调用时求值**，所以每次调用都重新读一遍 cwd 和环境变量。消费者不少：`server/config/boot-config.ts`、`server/database/config.ts` 都走这条路。

后果：`RuntimePaths` 承诺的「一次进程一份不可变根」**在实际调用路径上并不成立**。进程生命周期内 cwd 或 `NEURO_BOOK_STATE_ROOT` 一变，不同时刻的 `resolveStateRoot()` 就返回不同目录，而调用方按契约以为它恒定。`Object.freeze` 冻的是那个一次性对象，不是解析结果。

**这不是纯理论**。grep 显示至少 4 个测试文件必须 `process.chdir` 才能控制解析结果：

- `server/workspace-files/test-workspace-fixture.ts:187`
- `server/workspace-files/project-workspace-delete.test.ts:116 / :145`
- `server/utils/novel-chapter.test.ts:23`
- `server/database/config.test.ts`

**测试要靠改全局 cwd 才能测，本身就是这个耦合的直接症状。**

### 一个需要人来判断的假设

这些测试都在 `afterEach` 里 `process.chdir(originalCwd)` 还原。但**一旦某个用例在还原前抛出，同一个 fork 里后续测试文件的 cwd 就是错的**——而 vitest 的 fork 会串行跑多个文件。

这可能是 Task 123 记录的「全量套件 41–53 文件失败、两次运行用例总数相差 167、大量 5000ms 超时」的贡献因素之一。

**标为假设，不是结论**：本轮没有实测（要跑全量套件，MUST NOT 禁止），也没有确认 vitest 的 pool 配置。但这条线索的价值高于今夜多数 finding——**它可能解释那个一直没人查清的不稳定基线**。写进未决问题交给人。
