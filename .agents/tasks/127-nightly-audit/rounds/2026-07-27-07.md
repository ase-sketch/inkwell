## 发现

### F-013（medium）：`unlink()` 不中止在途的备份上传，数据继续传给刚解除关联的账号

`runBackup` 的时间线（`backup-job-manager.ts` 110–147）：

1. 第 115 行 `getAccessToken()` —— 先确认凭据可用
2. 第 117–120 行 **打包，耗时以分钟计**（整个 State Root：workspace + config.yaml + .env）
3. 第 125 行 `const fresh = await client.getAccessToken()` —— 把 token **拷进局部变量**
4. 第 136 行 用 `fresh.token` 上传

`unlink()` 做的是：best-effort 通知官方站吊销 → 删本地凭据行 → `accessTokenCache = null`。

**它清的是缓存，清不掉已经被拷进局部变量的那个 bearer token。** 所以用户在上传期间点「取消关联」：

- UI 报解除成功
- **上传照常跑完**，把整个 State Root 推到刚解除关联的账号
- 而且 `unlink()` 里对官方站的 revoke 失败是被 `catch {}` 吞掉的（第 154 行），吊销的只是 refresh token，access token 在其 TTL 内依然有效

「取消关联」这个动作的用户预期非常明确：**别再往那儿发我的东西了**。这里不满足。不需要竞态，只要上传在途——而整个小说 workspace 的上传本来就要跑一阵。

定 medium 不定 high 的理由：这批数据本来就是用户自己发起要上传的，窗口也被上传时长框住。但预期违背是实打实的。

修法：`PassportClientService` 需要一个「凭据代次」标记，`unlink()` 递增它；备份任务在每个网络分片前校验代次，不一致就中止上传。光清缓存不够。

### F-014（low）：`unlink()` 与并发 refresh 的竞态可能把凭据 upsert 复活

`refreshAccessToken()` 的顺序是 `findUnique` → `$fetch` token → `saveCredential`（upsert）。

若 `unlink()` 的 `delete` 恰好落在这个 `$fetch` 与 `saveCredential` 之间，upsert 会**把用户刚删掉的凭据行重新创建出来**，账号悄悄恢复关联。

窗口只有一次网络往返（约 100ms–1s），比 F-013 窄得多，所以定 low。但如果此时对官方站的 revoke 也失败了（会被吞掉），复活出来的就是一份**完全可用**的凭据。

同一个代次标记能一起修掉：`saveCredential` 前校验代次。

### F-015（low）：`linkSessions` 没有 TTL 清理，发起关联但不轮询就永久泄漏一个 deviceCode

`startLink` 每次 `this.linkSessions.set(...)`，删除只发生在 `pollLink` 的四条出口（成功 / expired / expired_token / access_denied）。

**用户点了「关联」然后关掉对话框，这条会话就永远留在内存里**，带着那个 `deviceCode`。没有定时清扫，只增不减。

单实例单用户，增长率很低，所以是 low。但它装的是一个凭据类的秘密，早就过期无用了还留着。修法：`startLink` 时顺手清掉 Map 里所有 `expiresAt < Date.now()` 的条目——一行 for 循环。

## 读对了但不是缺陷的地方（排除掉的怀疑）

- **`refreshInFlight` 的并发共享是对的**。第二个调用方走 `if (this.refreshInFlight) return await ...` 分支、不进 finally，只有发起方清空。注释里那句「两路并发各自轮换会让旧 token 双花，触发官方站整链撤销」说明作者清楚这个坑
- **`toStatus` 里的 `JSON.parse(credential.scopesJson)` 没有 try**，形状上像 F-006/F-008，但**数据源是 SQLite 列不是文件**，写入有事务原子性，F-006 的撕裂机制在这里不成立。不记 finding
- **`pollLink` 的 `slow_down` 处理正确**：`session.interval += 5` 并透传给前端，符合设备码流规范
