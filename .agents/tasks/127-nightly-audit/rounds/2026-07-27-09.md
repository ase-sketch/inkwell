## 结论：F-017 的机制描述错了，但结论成立，而且更严重

### 我上一轮写错的地方

第 8 轮我写的前提②是「`ensureStateFiles` 无条件写 `server: {host: "0.0.0.0", port}`，所以绑全网卡」。

**这个机制是错的。** `config.yaml` 里的 `server.host` **根本没有消费者**：

- `server/config/boot-config.ts` 的 `BootConfig` 类型**声明**了 `server?: {host?, port?}`，但整个文件只导出 `resolveBootAuthEnabled()` 与 `loadBootAuthEnabledSync()`——**只读 `auth.enabled`，从不读 `server`**
- grep 全 `server/`：无任何 `.server` 消费点
- grep 整个 Manager 包：`No matches found`
- `server/database/config.ts:22` 的注释把话说死了：「`.env` / 进程环境是执行真值源；`config.yaml` 只作为部署镜像和诊断输入」

所以我上一轮那句「不分 profile 无条件写 0.0.0.0」虽然字面属实，**却不是绑定发生的原因**——那行写进去的值谁也不看。

### 纠正后的机制（已在代码与依赖源码中逐级确认）

1. Portable 的 `.env` 由 `ensureStateFiles` 写出，内容只有 `NUXT_PORT` / `PORT` / `DATABASE_KIND` / `DATABASE_URL` / `NUXT_SESSION_PASSWORD`——**没有 `HOST`**
2. Manager 的原生启动路径也不设 `HOST`。全仓 grep `HOST` 只有三处设值：`Dockerfile`/`docker-compose`/`docker.ts` 设 `0.0.0.0`（容器语境，正确）、`health.ts` 设 `127.0.0.1`（探测用）、`verify-posix-product.sh` 设 `127.0.0.1`（验证脚本）
3. Nitro 的两个 preset 都是同一句：

   ```js
   // presets/node/runtime/node-server.mjs:18
   const host = process.env.NITRO_HOST || process.env.HOST;
   const listener = server.listen(path ? { path } : { port, host }, ...);
   // presets/bun/runtime/bun.mjs:9
   host: process.env.NITRO_HOST || process.env.HOST,
   ```

   `HOST` 未设 ⇒ `host === undefined` ⇒ `listen({port, host: undefined})` **绑所有接口**（Node 文档：省略 host 时监听未指定地址 `::` 或 `0.0.0.0`）

**⇒ 默认 Windows Portable 安装：`HOST` 从未被设置，Nitro 绑所有接口，而 `cli.ts:98` 让 `authEnabled` 默认为 false，`auth.ts` 的守卫因此整体空操作。结论与第 8 轮一致。**

### 为什么纠正后更严重

第 8 轮的版本里，`host: "0.0.0.0"` 是 `config.yaml` 里一个明晃晃的值——**用户看见了可以自己改成 `127.0.0.1`**。

真实情况是：**改了没用。** 那个字段没有消费者。一个察觉到风险、打开 `config.yaml` 把 host 改成 `127.0.0.1` 并重启的用户，会以为自己修好了，而服务照样绑在所有网卡上。

从「有个危险的默认值」变成了「有个危险的默认值 **且** 看起来能关掉它的那个开关是假的」。

### F-018（medium）：`BootConfig.server` 是只写不读的死字段

由此单独登记一条：`server.host` / `server.port` 在类型里声明、被 Manager 写进 `config.yaml`、在 `config.example.yaml` 里示范，**但全仓没有任何读取点**。

`server/database/config.ts:22` 的注释说 config.yaml「只作为部署镜像和诊断输入」，说明这是有意的分工。但**类型声明和示例配置没有跟着表达这件事**，读到这份配置的人（和写运维文档的人）会理所当然地以为它生效。

`auth.enabled` 是真读的，`server.*` 不是——**同一个文件里一半字段生效一半不生效，没有任何标记区分**。这比整个文件都不生效更容易骗到人。

## 本轮对巡检自己的意义

上一轮的 F-017 如果就那样进早报，会发生两件事：

1. 修的人按我给的机制去改 `ensureStateFiles` 里那行 `host`，**改完问题还在**
2. 我给的另一个修法「host 默认跟随 profile 条件」同样无效，因为那个值没人读

**一条 high 的机制写错，比漏掉这条 high 更糟**——它会把人引到一个改完没用的地方，然后让人以为修好了。这正是上一轮 checklist 写下「生成侧与消费侧要分别验证」的原因，本轮是它的第一次兑现。

正确的修法是：Portable profile 的启动路径显式设 `HOST=127.0.0.1`（或让 `.env` 带上它），**并且**让 `config.yaml` 的 `server.host` 要么真被消费、要么从类型和示例里删掉。
