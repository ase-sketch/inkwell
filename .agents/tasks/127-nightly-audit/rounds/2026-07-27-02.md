## 发现

### 上一轮 F-001 的悬案已答：资产同步**不是**原子写入

`syncManagedSystemAssetsToUserAssets` 的三处写入全是 `await fs.copyFile(systemPath, userPath)`（第 555、577、609 行），就地截断重写，没有临时文件 + rename。

所以 F-001 描述的「启动窗口内被 SIGTERM 打断」确实会在 user-assets 里留下**半截文件**。

**更要命的是它不自愈。** 追下一次启动会怎么处理这个半截文件（`options.force` 为 false，因为 `product-start.mjs` 只传 `--sync-user-assets` 不传 `--force`）：

- 有 sync state 时：`currentUserHash !== stateItem.lastSyncedUserHash` 成立 → 落到第 594–601 行 → 报 warning「系统 .nbook asset 已更新，但用户覆盖已手改，未自动覆盖」→ `continue`
- 没有 sync state 时（状态文件是循环结束后才写的，中途崩就没写成）：落到第 587–593 行 → 报 warning「有 metadata，但用户覆盖缺少 sync state，已保留用户文件」→ `continue`

两条路都是**永久保留半截文件，并把它误报成「用户手改」加以保护**。用户看到的是一句「你改过这个文件所以我没覆盖」，而他根本没改过。

这条独立登记为 **F-005（medium）**。F-001 保持 medium，但在 `FINDINGS.md` 里补上了「后果由 F-005 承载」的交叉引用。

### F-006（high）：sync state 文件同样非原子写，而读取端只兜了 ENOENT

`writeUserSystemAssetsSyncState`（第 1474–1478 行）：

```ts
await fs.writeFile(userSystemAssetsSyncStatePath(), `${JSON.stringify(syncState, null, 2)}\n`, "utf-8");
```

就地截断重写，非原子。而 `readUserSystemAssetsSyncState`（第 1459–1472 行）的 catch **只处理 `error.code === "ENOENT"`**，其余一律 `throw`——包括 `JSON.parse` 抛的 SyntaxError。

于是这条链成立：

1. 写 sync state 的瞬间被打断（F-001 的窗口、掉电、容器被杀、磁盘满）→ 文件半截，JSON 不合法
2. 下次启动 `readUserSystemAssetsSyncState` 抛 SyntaxError
3. 往上冒泡穿过 `syncSystemAssetsToUserAssets` → `prepareSystemAssets`
4. `product-start.mjs` 第 14 行是**顶层 await 且没有 try/catch**，子进程非零退出让 `run()` reject → unhandled rejection
5. **Product 起不来**，而且每次重启都一样，直到有人手动去删那个 JSON

定 high 的理由是「线上不可用 + 不自愈 + 报错信息完全不指向真正的原因」。用户看到的是一段 JSON 解析栈，没有任何线索告诉他该去删哪个文件。

两处修法都很小：写入走临时文件 + rename；读取时把「解析失败」和「文件不存在」同等对待——**这个文件本来就是派生缓存**，第 547 行那条「用户文件与系统文件相同就重新登记状态」的分支证明了丢掉它是可以重建的。

### 定级说明

F-006 定 high，但**没有推通知**。理由已写进 skill 的「通知」节：严重度不等于紧急度。这是静态阅读读出来的既有缺陷，在代码里躺了很久，今晚不会恶化，半夜叫醒人也只能等到早上才动手。
