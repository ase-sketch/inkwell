## 发现

### F-010（medium）：备份排除规则按文件名后缀匹配，没有目录作用域

```ts
const name = normalized.split("/").pop() ?? "";
return name.endsWith(".lock") || name.endsWith(".tmp") || name.endsWith("-wal") || name.endsWith("-shm");
```

注释写的意图是「锁文件、临时文件、SQLite wal/shm 伴生文件」，实现却是「**树里任何位置、任何文件，只要名字这样结尾就排除**」——包括用户的 manuscript 目录。

一个叫 `草稿.tmp` 的稿子会**静默地、永久地不出现在任何一次备份里**。

这条和 F-009 的性质不同，更棘手：F-009 至少有个被吞掉的错误，理论上能被错误处理捕获；**排除规则根本不产生错误**，无论错误处理写得多好都发现不了。备份还是最后一道防线，它的失败只在用户已经出事时才暴露。

概率不高（有几个人会把小说存成 `.tmp`？），但代价是静默且不可逆，所以定 medium 而不是 low。

修法：wal/shm 的排除范围收敛到「同目录下确实存在同名 `.sqlite` 文件」，或至少限定在 `.nbook/` 目录内；`.lock` / `.tmp` 同理。

### F-011（low）：`isSqliteFile` 与其他地方对 DB 扩展名的口径不一致

`isSqliteFile` 只认 `.sqlite`：

```ts
return relativePath.replaceAll("\\", "/").endsWith(".sqlite");
```

而 `server/workspace-files/workspace-files.ts` 第 151/179/180 行同时登记了 `.db`、`.sqlite`、`.sqlite3`。

已 grep 确认**今天全仓所有 DB 都叫 `*.sqlite`**（`neuro-book.sqlite` / `project.sqlite` / `history.sqlite` / `subject-rag.sqlite`），所以这条现在打不着。但一旦将来有 DB 用了 `.db` 或 `.sqlite3`：

1. `isSqliteFile` 返回 false → **不走 VACUUM INTO 冷快照**，活库被原样拷贝
2. 它的 `-wal` 却仍被后缀规则排除
3. 结果是备份里一个**缺了未 checkpoint 写入的残库**，且没有任何提示

埋雷，与 F-004 同类。定 low。

### 反面结果：`workspace-history` 的裸 catch 全是对的，机械化扫描这条路基本失效

上一轮登记的第 2 项是「全仓 grep 裸 `catch {`」。结果：**106 处，分布在 69 个文件**。

抽最高危的 `server/workspace-history/`（操作日志真相源，7 处）逐个读，**没有一处是缺陷**：

- `agent-file-recorder.ts:72 / :78` —— 注释写明「记账永远不能反向破坏文件写入」。用户的文件已经落盘，记账失败不该回滚它。优先级判断正确且写下来了
- `agent-change-diff.ts:102` —— catch 里写 `details.set(group.path, {kind: "unavailable", reason: "history_error"})`，**把降级如实呈现给 UI**
- `project-history.ts:146 / :585` —— 注释写明「路径策略错误按 fail-open 记账入口的既有语义降级为不消费」，是有意的既有语义

**所以「裸 catch」本身不是缺陷信号，106 这个数字没有任何意义。** 真正的判别式是两条：

1. **被吞掉的失败在别处可见吗？**（记进 warnings / 呈现为 unavailable / 写日志）
2. **注释描述的范围与代码实际吞掉的范围一致吗？**

F-009 两条都不满足（无上报通道 + 注释说「目录不存在」而代码吞一切），`workspace-history` 两条都满足。这两条判别式已写进 `CHECKLIST.md`。

**教训：grep 出的模式只是候选池，不是发现。** 本轮如果直接把 106 处当成待办报出去，早报就毁了。
