## 发现

### 本轮最重要的一条：上一轮那个「显而易见的修法」是错的

第 2 轮我给 F-005 写的修法建议里，隐含着一个想当然：既然 `fs.copyFile` 不安全，那就该用别的。而 profile 与 variable 两条同步链**确实**用了看起来更讲究的 `replaceFileWithRollback`。

如果早报只写到这里，最自然的动作就是「把 asset 链也改成 `replaceFileWithRollback`，收工」。**那样什么都没修好。**

读 `replaceFileWithRollback`（1410–1441）：

1. `fs.copyFile(targetPath, backupPath)` —— 先备份
2. `fs.copyFile(sourcePath, targetPath)` —— 就地截断重写
3. `catch` 里从备份恢复
4. `commit()` 删掉备份

它防的是**本进程内抛异常**（比如随后的 artifact staging 失败要回滚），不是**进程被杀**。第 2 步依然是就地截断重写，进程死在这一步，目标文件照样是半截的，而且 `catch` 根本不会执行。

**结论：三条同步链的崩溃窗口完全一样。** F-005 的影响面是全部三条，不是只有受管 asset。名字里的 "rollback" 指的是事务回滚，不是崩溃原子性——这个名字很容易让人以为问题已经解决了。

登记为 **F-007（medium）**，同时把 F-005 的影响面从「受管 asset」扩到「三条链」。

F-007 还带一个次要后果：进程死在第 2 步与 `commit()` 之间时，`<目标>.{uuid}.backup` 会留在用户的 `.nbook/agent/profiles/` 里，**没有任何启动时清理路径**，会随每次崩溃累积。（这些 `.backup` 文件会不会被 profile 扫描器当成 profile 加载，本轮没查。）

### F-008（high）：同一个模式，在更要害的位置

grep 全 `server/` 找同类读取点，非测试文件里最要害的一处是 `server/config/config-service.ts`。因为该文件此刻是热区，用 `git show HEAD:` 读的**已提交版本**：

```ts
async function readJsonFile<T>(filePath: string): Promise<T | null> {
    try {
        return JSON.parse(await fs.readFile(filePath, "utf-8")) as T;
    } catch (error) {
        if (... error.code === "ENOENT") { return null; }
        throw error;
    }
}
// readJsonFileSync 同构
async function writeJsonFile(filePath: string, value: unknown): Promise<void> {
    await fs.mkdir(path.dirname(filePath), {recursive: true});
    await fs.writeFile(filePath, `${JSON.stringify(value, null, 4)}\n`, "utf-8");
}
```

与 F-006 **逐字同构**：写入非原子，读取只兜 `ENOENT`、把 `JSON.parse` 的 SyntaxError 直接抛。

但这次的对象是 **Global Config 与 Project Config**（`workspace/.nbook/config.json`），里面是模型 provider、鉴权、各种设置。它比 sync state 严重两个层次：

1. **写得频繁得多**。sync state 只在启动同步时写一次，config 是用户每改一次设置就写一次——崩溃窗口被命中的概率高一个量级
2. **它是真正的用户数据**，不是派生缓存

第 2 点直接决定修法必须和 F-006 不同：

- F-006 的 sync state 可以「解析失败就当文件不存在」，因为它能重建
- **F-008 的 config 绝对不能这么修**——那等于用户改坏一次就把 API key 和全部设置静默清空

config 这边唯一正确的修法是**写入原子化**（临时文件 + rename），外加一句指名道姓的错误信息（「`<路径>` 内容已损坏，请检查或删除后重启」），而不是自动丢弃。

**「把 F-006 的修法套到所有同类点」会在这里造成数据丢失。** 这一条必须写进早报。

### 第 2 轮的假设得到验证

三条同步链 + sync state + config，五个点全是同一个缺口：**全仓没有一个「原子写 JSON / 原子替换文件」的公共 helper，每处各写各的，最讲究的那个（`replaceFileWithRollback`）也只做到事务回滚**。

所以这不是 5 条独立 finding，是 1 个缺失的基础设施 + 5 个受害点。早报应该按这个结构写，而不是罗列五条。
