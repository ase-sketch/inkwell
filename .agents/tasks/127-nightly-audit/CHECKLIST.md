# 夜审检查清单

可自我修订，**只增不删**，删除条目须人工。超过 20 条后每轮只挑与当前方向相关的过。

## 通用

- [ ] 类型覆盖漏洞：`any` / `unknown` / `Record<string, unknown>` 的使用是否有正当理由，旁边有没有写原因
- [ ] 错误处理路径：异常被吞、错误被转成成功、catch 里只 log 不处理
- [ ] 并发与竞态：共享状态、缺锁、await 顺序假设
- [ ] 资源泄漏：未关闭的句柄、未清理的监听器与定时器、未 kill 的子进程
- [ ] 文档与代码漂移：文档或 `reference/` 描述的行为与实现不符
- [ ] 测试覆盖空洞：复杂分支无测试、测试只覆盖 happy path
- [ ] 陈旧 TODO：引用了已不存在的文件、函数或任务编号
- [ ] 跨模块契约不一致：同一概念在两处有不同定义或校验

## 第 1 轮学到的（进程与生命周期方向）

- [ ] **信号处理器的注册时机**：`process.on("SIGTERM")` 是不是排在所有顶层 `await` 之前？await 期间是一段无处理器的裸奔窗口
- [ ] **`once` 与 `on` 用错**：停止信号、错误事件这类可能重复到达的，用 `once` 就等于只处理第一次
- [ ] **`exitCode` 与 `signalCode` 口径不一致**：同一文件内若一处只判 `exitCode`、另一处两个都判，只判一个的那处必是漏改（死于信号时 `exitCode` 恒为 `null`）
- [ ] **`exit` 与 `close` 用错**：需要读完 stdout/stderr 的，必须听 `close`；`exit` 早于 stdio 关闭
- [ ] **选项类型声明了但实现不支持的值**：例如 `stdio` 允许 `"pipe"` 却从不消费管道。类型系统在这里是在发邀请函，第一个接受邀请的调用方就中招
- [ ] **测试把慢步骤桩成瞬时**：桩掉的那一段往往正是要测的时间窗口（`product-start.test.ts` 把资产同步桩成 `process.exit(0)`，启动窗口被压成 0）

## 第 2 轮学到的（持久化与崩溃恢复方向）

这一组配套用，单看一条都不够：

- [ ] **写入是否原子**：裸 `fs.writeFile` / `fs.copyFile` 都是就地截断重写，被打断就留半截文件。要原子必须临时文件 + `rename`
- [ ] **读取端有没有为「文件在但内容坏了」留退路**：只兜 `ENOENT` 是最常见的漏法——不存在能兜住，损坏却直接抛
- [ ] **损坏之后能不能自愈**：跟着代码走一遍「下次启动会怎么处理这个坏文件」。走不到修复分支，就是永久故障
- [ ] **派生数据有没有被当成用户数据保护**：缓存 / 索引 / 同步状态本来可以重建，若代码把它们当成不可再生的东西小心翼翼保留，损坏就永远修不好
- [ ] **报错信息指不指向真正的原因**：一段 JSON 解析栈不会告诉用户该去删哪个文件
- [ ] **顶层 `await` 有没有 try/catch**：入口脚本里一个未捕获的 reject 就是整个进程起不来
- [ ] 上面几条**要串起来看**：单独看「非原子写」只是 low，串上「读取不兜错 + 不自愈 + 顶层无 catch」才看得出它是 high

## 第 3 轮学到的（怎么不把结论做错）

- [ ] **名字里的保障词要当场验证**，别信 `safe` / `atomic` / `rollback` / `ensure` / `guard`。`replaceFileWithRollback` 的 rollback 指的是进程内事务回滚，不是崩溃原子性——不读实现就会把它当成 F-005 的现成修法
- [ ] **同一个缺陷模式，修法可能因数据性质而相反**。派生缓存损坏了可以丢弃重建，用户数据损坏了丢弃就是数据丢失。写「统一按 X 修」之前，先给每个受害点标上「这是缓存还是用户数据」
- [ ] **找到第三个同类点时停下来换个写法**：不再逐条罗列，改写成「一个缺失的基础设施 + N 个受害点」。前者能被一次修掉，后者会被修成 N 个各不相同的补丁
- [ ] **热区文件用 `git show HEAD:<path>` 读已提交版本**，别放弃这块地。改动在途 ≠ 不能审，只是不能审工作副本
- [ ] 想跑的命令不在白名单里时，**先把它连同限制一起登记进白名单再跑**，不要绕过。绕一次这张表就不再是判据了

## 第 4 轮学到的（错误处理口径，本仓库命中率最高的一组）

**核心一句：每个 `catch` 都要说清楚，我想放过的是哪个 errno？** 下面几条都是它的展开。

- [ ] **裸 `catch {}` 后面跟 `return` / `continue` / 空体**——这是静默丢数据的标准形状。尤其在收集、扫描、遍历类函数里
- [ ] **注释与 catch 宽度不符**：注释写「文件不存在时跳过」而代码是裸 catch（吞掉权限和 I/O 错误），或者注释说要容错而代码只认 `ENOENT`。**两个方向都要查，症状相反病因相同**
- [ ] **失败上报通道存在却没接**：函数返回值里有 `warnings` 之类的字段，但某个子函数的签名里没有它——那个子函数的失败就是无声的
- [ ] **成功返回值会不会掩盖部分失败**：备份返回了 sha256 和 fileCount，看起来权威，但少收了一棵子树它一样能返回
- [ ] **同一文件内先找正面样板再定修法**：本仓库多次出现「同一个文件里既有写对的也有写错的」，照抄同文件的正确写法比新发明可靠，也更容易过审
- [ ] **别预设结论**：第 4 轮预判备份链会重复 F-006 的模式，实际读出来是对的，真正的问题在反方向。**预判要写进 round 文件，被推翻时如实记下来**

## 第 5 轮学到的（怎么判一个 catch 是不是缺陷）

实测：全仓 106 处裸 `catch {`，抽最高危的 `workspace-history` 7 处逐个读，**一处缺陷都没有**。所以裸 catch 本身不是信号。判别式只有两条，两条都不满足才是缺陷：

- [ ] **被吞掉的失败在别处可见吗？** 记进 warnings、呈现为 `{kind:"unavailable"}`、写日志——只要有一条通道，就是有意降级不是缺陷
- [ ] **注释描述的范围与代码实际吞掉的范围一致吗？** 注释写「目录不存在时跳过」而代码裸 catch，是缺陷；注释写明「记账失败不能反向破坏文件写入」并确实只吞记账，是正确决策
- [ ] 判定「有没有上报通道」要**先看函数签名有没有 warnings/result 之类的出参**，而不是盯着 catch 本身看
- [ ] **grep 出来的是候选池，不是发现。** 把 106 处当待办报出去，早报就毁了。机械化扫描只负责缩小范围，逐条判定仍然只能靠读

## 静默失败的三个层次（第 4、5 轮合并出来的）

按「能不能被发现」排序，越靠后越难查：

- [ ] **有错误、被吞了**——F-009。错误处理写对就能捕获
- [ ] **有错误、没吞但报错误指向错了**——F-003 的 `signalCode` 漏判、F-006 的 JSON 栈。能查，但会把人引向错误方向
- [ ] **压根没有错误**——F-010 的排除规则。规则写宽了不产生任何异常，**再好的错误处理也发现不了**，只能靠读规则本身或对比预期清单。查完错误处理后，务必再问一句：有没有哪条「正常路径」本身就会丢东西？

## 第 6 轮学到的（关于巡检自己）

- [ ] **抄来的地基要验**。`AUDIT-STATUS.md` 的噪音基线若是从项目文档抄的，它就是传闻。整套机制的发现质量都压在它身上：数字偏小 → 每晚几十条假发现，数字偏大 → 真错误被当噪音放过。**闸门第一次打开时，优先验它，而不是验某条 finding**
- [ ] **白名单里的耗时估计也要实测**。原表把 typecheck 记成「~3-5min」，实测 40 秒——这个错数让前五轮一直高估它的代价，影响了每轮「要不要跑」的判断。跑过一次就把真实耗时写回表里
- [ ] **一条线查完了要在覆盖率地图上写「已查完，不要再回头」**，否则下一轮容易被熟悉的线索吸回去。同一模式的第 6、7、8 个实例边际价值极低，早报的结论不会因此改变
- [ ] **负面结果要显式记下来**：「恢复侧不共享排除规则」「`sanitizeZipEntryName` 的 null 处理是对的」——这些是排除掉的怀疑，下一轮不必重查，价值不低于 finding
- [ ] **连查同一类问题超过三轮就该换方向**。第 7 轮从持久化换到鉴权面，一轮出三条——方向多样性本身有价值，同一条线的第 6、7 个实例改变不了早报的结论

## 第 7 轮学到的（撤销、失效与凭据生命周期）

- [ ] **「撤销」到底撤掉了什么？** 清缓存 ≠ 失效凭据。已经拷进局部变量、已经在飞行中、已经发给下游的东西，清缓存一概管不住
- [ ] **长流程里把 token 拷进局部变量**（`const {token} = await getAccessToken()` 然后跑几分钟），这个局部变量就是撤销够不着的地方。判据：**从取 token 到最后一次用它，中间隔了多久？**
- [ ] **撤销后有没有代次/版本标记让消费点自检？** 没有的话，撤销只是把引用抹了，实际权限还在
- [ ] **「先删本地再通知远端」还是反过来？** 且远端通知失败被吞掉时，本地状态是不是已经声称成功了
- [ ] **内存里的会话 Map 有没有 TTL 清扫？** 只在成功路径删除的 Map，一定会被「用户中途放弃」这条路径喂成只增不减
- [ ] **注释把校验推给别人时要跟过去看**：「协议合法性由 DTO schema 保证」这类话是**待验证的断言**，不是结论。第 7 轮就在这里留了个没跟完的线索
- [ ] 判断竞态严重度时**要量出窗口宽度**：一次网络往返（~1s）和一次打包上传（~几分钟）是两个量级，直接决定 low 还是 medium

## 第 8 轮学到的（默认值的组合，比单个默认值危险）

- [ ] **单看每个默认值都合理，组合起来才是洞。** 「桌面应用免登录」合理，「服务默认绑 0.0.0.0」在服务器语境下也合理——**配到一起就是把用户的全部数据挂在局域网上**。查配置默认值时一定要问：这几个默认值会同时生效吗？
- [ ] **默认值分不分 profile？** F-017 的要害是 `auth.enabled` 跟着 profile 走而 `server.host` 不跟——**一个变量分了档，另一个没分，中间就漏出一个没人设计过的组合**
- [ ] **为本地开发开的口子有没有限定在本地？** 允许 `http://` 是为了本机 dev 站，但规则写成了「任意主机的 http」。判据：这条豁免有没有绑定 `localhost` / `127.0.0.1` / `[::1]`
- [ ] **守卫可以被整体关掉吗？** `if (!enabled) return;` 这种形状意味着守卫的强度完全取决于那个开关的默认值和可达性，守卫本身写得再好也没用
- [ ] **生成侧与消费侧要分别验证。** 读到「配置文件里写了 X」只证明生成侧写了 X，**不证明运行时真的按 X 生效**。一条建立在配置默认值上的 finding，必须两侧都走到，否则宁可降级
- [ ] **一条 high 建立在 N 个前提上时，逐条标注哪些已在代码确认、哪些还是文档说法。** 早报里报一条站不住的 high，比漏报更消耗信任

## 第 9 轮学到的（配置字段有没有消费者）

第 9 轮把第 8 轮 F-017 的机制描述推翻了：`config.yaml` 的 `server.host` 根本没人读。结论侥幸没变，但**给出的修法全是无效的**。

- [ ] **看到一个配置字段，先 grep 它的读取点，再谈它的影响。** 「类型里声明了」「示例配置里有」「生成侧写了」三样加起来都不证明它生效
- [ ] **同一个配置文件里，字段可能一半生效一半不生效**（这里 `auth.enabled` 真读、`server.*` 不读），且没有任何标记区分。**逐字段查，不要按文件下结论**
- [ ] **死配置字段比没有这个字段更危险**：它让察觉到问题的人改一改就以为修好了。查到「只写不读」的字段要单独记一条
- [ ] **环境变量与配置文件谁是真值源？** 本仓库注释写死了「`.env` / 进程环境是执行真值源，`config.yaml` 只是部署镜像和诊断输入」——这类分工要先找到并读懂，否则整条推理都建在错的层上
- [ ] **默认值缺失也是默认值**：`HOST` 未设 ⇒ `listen({host: undefined})` ⇒ 绑所有接口。查「配了什么」的同时要查「没配会怎样」，后者往往才是真实生效的那条路径
- [ ] **追到框架/依赖源码为止**（本仓库允许读 `node_modules`）。「Nitro 默认绑哪」不能靠记忆，`presets/node/runtime/node-server.mjs` 一行就写着

## 报错一条 high 的代价（第 9 轮的教训，值得单列）

- [ ] **机制写错的 high 比漏报的 high 更糟**：修的人按错误机制去改，改完问题还在，而他以为修好了。**结论对不等于可以交付**——早报给出的每条修法都必须落在真正生效的那一层
- [ ] 因此：**任何一条 high，落笔前把「按我写的修法改完，问题真的会消失吗」在脑子里跑一遍**

## 第 12 轮学到的（观测者把自己算进了观测结果）

第 12 轮发现 Phase 1 的工作区基线把夜审自己写的文件也数了进去（136 行里有 6 行是自己的），于是「别人有没有在动」这个信号被自己的写入污染。**前十一轮没暴露，是因为 Task 118 真的在改——真实的并发把这个 bug 完美地盖住了。**

- [ ] **任何「有没有变化」的探针，先问它有没有把自己的动作算进去。** 巡检、监控、diff、计数器都适用
- [ ] **两个原因表现相同时，先怀疑自己那个。** 「基线变了」既可能是别人在改也可能是自己在写；后者是可以直接排查的，前者只能猜
- [ ] **差值很小又很整齐时（+1、+2）要起疑。** 别人的批量改动通常是十几个文件，正好 +1 更像是自己刚建了一个文件
- [ ] **侥幸没出事不等于没 bug**：写进已存在目录不改变行数，所以这个缺陷藏了十一轮；第一次新建顶层文件就暴露了
- [ ] 修完探针后**旧数据与新数据不可比**，要显式记下口径变更，并按保守方向处理那一轮（视同已变化）
